# 整合方案 · Web 单栈版（双模式剧情游戏）

> **决策**：放弃 Godot 作为最终载体，全栈搬到 Web（React 主壳 + Phaser 场景）。
> **形态**：**地图探索 + 手机聊天** 双模式推进同一套剧情，中间穿插任务小游戏。
> **基调**：全程 2D 像素动画风，动效与特效做足。
>
> 配套阅读：`设计/交接文档.md`（美术规范与铁律）、`设计/项目总纲.md`、
> Godot 旧工程的 `STORY_BIBLE.md` / `剧本.md` / `规则书.md`（**剧本与规则的唯一真源，继续沿用**）。

## 0. 为什么这个组合是对的

旧 Godot 版的剧本是**聊天式**的。纯 AVG 里，"聊天"只是一个界面；
但加上地图走动之后，它变成了**世界观的一部分**：

> **刘看山在办公区走动，手机在口袋里震。他掏出手机——群聊正在刷屏。**

于是两种模式有了清晰分工：

| 模式 | 承载 | 玩家感受 |
|---|---|---|
| **手机（ESC）** | **信息**：群里发生了什么、谁私聊你、任务要求是什么 | 我在读消息、在做判断 |
| **地图（默认）** | **行动**：去会议室、去工位、去客户公司、把文件送到门口 | 我在办公室里真的走过去了 |

**两条线在关键时刻交叉**：

```
手机里林总说「下午三点程女士要看初稿」
        ↓
地图上出现指引线，指向会议室
        ↓
走过去 → 触发事件四·客户拜访
        ↓
谈完回到工位 → 手机震 → 事件五·会议异议
```

这条设计线让"为什么要走路"和"为什么要看手机"都成立，而不是两个割裂的玩法。

### 关键语义转换

**ESC 不是"暂停菜单"，是"掏出／收起手机"。**

- 按 ESC → 手机从屏幕下方滑入，地图暂停并轻微虚化
- 再按 ESC → 收起手机，回到地图
- 真正的设置/存档/重开，做成手机里的一个 **「设置」标签页**

这个转换让 ESC 有了叙事意义，也顺带把暂停功能自然藏了起来。

## 1. 三种模式的关系

```
┌──────────────────────────────────────────────────────────┐
│  地图模式（Phaser）    ← 默认状态，可自由走动              │
│   · 瓦片地图 · 主角四方向行走 · NPC · 指引线 · 交互点       │
└────────┬──────────────────────────────┬──────────────────┘
         │ 走近 NPC / 手机震动           │ 走近交互点
         ▼                               ▼
┌──────────────────────┐      ┌──────────────────────┐
│ 手机模式（DOM 浮层）   │      │ 小游戏模式（Phaser）  │
│  · 微信三栏 · 消息流   │───→  │  · 事件八 胡闹厨房     │
│  · 选项 · 跑团输入     │ 卡片 │  · 事件六 PPT 整理     │
│  · 知乎卡 · 设置       │  跳转 └──────────────────────┘
└──────────────────────┘
```

**三种推进剧情的方式**（玩家的原话："既可以在地图上走动推进，也可以打开 ESC 用聊天框推进"）：

1. **走近即触发**：地图上某个 NPC 头顶有光点，走过去自动开始对话
2. **手机自动弹**：剧情需要时手机震动，右上角出现提示，玩家自己决定什么时候看
3. **玩家主动聊**：任何时候打开手机，在联系人列表里找人说一句话（有限度的自由对话）

## 3. 地图设计

### 3.1 场景清单（先做一个，其余预留）

| 场景 | 用途 | 优先级 |
|---|---|---|
| **看山创意部 · 工位区** | 主场景，事件 1/2/3/6/7/8/9 的手机事件在这里"发生" | P0 |
| **会议室 A** | 事件 5、10 | P0（可以在工位区里用一扇门切换，或做成同场景的一个区域） |
| **茶水间** | 事件 3 | P1 |
| **客户公司 12 楼** | 事件 4 | P1 |
| **招聘会大厅** | **序章 / 回忆**（用我已有的招聘会素材） | P2 |

**第一版就做一个"看山创意部"大场景**，包含工位区 + 会议室门口 + 茶水间角 + 大门口，用一张地图装下，避免频繁切场景。

### 3.2 指引线（玩家明确要求）

这是地图模式的核心 UX。**不做成一条线，做成地面上的"流动光点路径"**：

```
玩家 ──●──●──●──●──▶ ◎ 目标（脉冲光圈）
       ↑ 光点依次亮起，向目标方向流动
```

**实现思路**：

1. 用 **A\* 寻路**从玩家格到目标格求路径（地图是瓦片网格，复用我已有的 BFS 实现）
2. 沿路径每隔 2 格放一个**箭头地贴精灵**（我已有 `箭头地贴` 素材）
3. 给每个箭头一个**相位偏移**，用 `tween` 做"依次点亮 → 熄灭"的流动效果
4. 目标点放一个**脉冲光圈** + 头顶一个浮动图标（手机／对话／门）

**多目标时**：指引线只指向**当前剧情目标**（金色），其他可交互点用**蓝色微光**表示可选。

**靠近后**：路径光点淡出，交互提示浮出（`空格 · 查看`）。

### 3.3 地图上的角色

| 角色 | 需要什么动画 | 素材量 |
|---|---|---|
| **刘看山（主角）** | 四方向行走 4 帧 + 待机呼吸 + 看向玩家 | 32 帧（已有 3 视图 + 4 帧侧面，**需补完**）|
| **林总 / 周岚 / 阿麦 / 韩策 / 小鹿 / 程女士** | **站立 + 朝向玩家 + 待机小动作**（点头/抱臂/看手机） | 每人 4–6 帧，**不做行走** |

> **重要取舍**：6 个 NPC 各做四方向行走 = 6 × 16 = 96 帧，性价比极低（他们绝大多数时间站着说话）。
> **只做"站立 + 朝向 + 小动作"，需要走动的场合用位移 tween 代替。**
> 这样素材量从 ~130 帧降到 ~40 帧，观感几乎无损。

## 4. 手机模式：像素风但清晰（关键技术点）

玩家要求："**2d 像素风格但是要清晰**"。这一条有唯一正解：

> **像素感来自"框"，清晰度来自"字"。两者分开做。**

| 层 | 做法 |
|---|---|
| **外框 / 气泡 / 头像 / 图标 / 按钮** | 用**像素素材**（PNG + `image-rendering: pixelated`） |
| **文字** | 用 **DOM 渲染**（矢量，永远清晰） |

### 4.1 必须引入中文像素字体

否则"像素风的框 + 平滑的中文字"会打架。推荐（都是开源可商用）：

| 字体 | 规格 | 备注 |
|---|---|---|
| **方舟像素字体 Ark Pixel Font** | 10 / 12 / 16 px | OFL 开源，中日韩覆盖好，**首推 12px** |
| **Zpix（最像素）** | 12 px | 覆盖广，社区常用 |
| **Fusion Pixel Font（缝合像素字体）** | 8 / 10 / 12 px | OFL，多字重 |

**铁律**：字号必须是字体原生尺寸的**整数倍**（12 → 12 / 24 / 36），
否则点阵会被浏览器重采样，立刻糊掉。**这是像素字体的唯一死法。**

### 4.2 微信三栏布局（沿用旧工程规则）

```
┌──────┬────────────────┬──────────────────────────────┐
│ 头像 │ 看山创意部 (6)  │                              │
│ 会话 │ 周岚           │        当前聊天区             │
│ 通讯 │ 林总           │   · 消息逐条出现（0.8–4 秒）   │
│ 设置 │ 阿麦           │   · 正在输入…（仅一对一）      │
│      │ 小鹿           │   · 选项 / 跑团输入框          │
│      │ 茶水间 (4)     │   · 知乎卡 ×2                  │
└──────┴────────────────┴──────────────────────────────┘
```

旧工程 `AGENT_HANDOFF.md` §1 的 8 条体验原则**全部继续生效**（消息逐条、
跨联系人隔离、AI 不改分数、收束顺序固定、不伪造知乎来源……）。

## 11. 取舍与风险

| 风险 | 应对 |
|---|---|
| **两个模式让开发量翻倍** | M0 先只做一个场景 + 两个事件，验证"走↔聊"的手感；手感不对就砍地图 |
| **6 个 NPC 四方向行走素材量爆炸** | 只做站立朝向 + 小动作，位移用 tween（见 §3.3）|
| **地图上走路可能变成"跑腿"** | 指引线要短（同一场景内），一次走动不超过 10 秒；长距离用转场 |
| **像素字体缺字** | 选覆盖 GB2312+ 的字体（方舟/Zpix），并保留系统字体兜底 |
| **中文像素字体在手机上糊** | 字号严格取 12 的整数倍；`font-smooth: never` |
| **旧剧本 10 事件的分数阈值是旧版** | 按 `通关走查.md` §15.1 重新配平（旧工程已知问题）|
| **知乎卡没有真实数据** | 沿用旧规则：**显示明确占位，绝不伪造作者与链接** |

## 13. 双端适配（PC 与移动端同等重要）

> 这一条是**铁律**（见 `设计/交接文档.md` §5.2）：两端都是一等公民，不是"PC 为主手机适配"。

### 13.1 先把一个矛盾解决掉：手机模式在真手机上会"套娃"

游戏里的"手机"是**刘看山的手机**（微信）。在 PC 上很自然：电脑屏里的办公室，主角掏出手机看微信。

**但玩家在真手机上玩时，手里就是一个手机，游戏里再掏出一个手机 → 套娃。**
而且手机屏小，微信的**三栏布局根本放不下**（真微信在手机上本来就是"列表 → 点进 → 聊天"两级）。

**解决**：**两端用不同的"呈现方式"，但共用同一套素材与数据。**

| | PC（横屏 / 512×288） | 手机（竖屏 / 288×512） |
|---|---|---|
| **地图模式** | 大视野，HUD 放两侧黑边 | 窄视野，HUD 上下窄栏 |
| **掏手机的表现** | 屏幕中央**浮出一块手机**，四周办公室虚化 | **直接全屏切到聊天界面**（不做套娃） |
| **聊天布局** | **三栏常驻**：功能栏 / 会话列表 / 聊天 | **两级导航**：列表 → 点进聊天 → 返回 |
| **收手机** | ESC | 顶部返回箭头 |

**核心决策**：移动端**不做"浮出一块手机"的效果**——玩家手里就是手机，全屏才是符合直觉的形态。

### 13.2 操作对照

| 操作 | PC | 手机 |
|---|---|---|
| 移动 | `W A S D` / 方向键 | **点按地面自动寻路**（点哪走到哪） |
| 交互 | `空格` / `E` | 点交互点（放大热区） |
| 掏手机 | `ESC` | 屏幕右下角的**手机按钮**（带未读红点） |
| 收起手机 | `ESC` | 顶部返回箭头（一级级退） |
| 聊天导航 | 三栏常驻 | 列表 ⇄ 聊天 两级 |
| 跳过消息 | 长按 0.8 秒 | 长按 / 双击 |

> **点按寻路 + 指引线是天然一对**：手机上玩家点一下指引线的目标点，主角自己走过去。
> 比虚拟摇杆更精确、单手可玩，而且和 PC 的"自己走"体验一致。

### 13.3 像素与字号

- 内部分辨率：横版 **512×288**（16×9 瓦片）/ 竖版 **288×512**（9×16 瓦片）
- **只允许整数倍缩放**，配 `image-rendering: pixelated`
- 中文像素字体字号**必须是原生尺寸的整数倍**（12px 字体 → 只能 12/24/36）
  - PC：聊天正文 **24px**（×2，看得清且点得准）
  - 手机：聊天正文 **24px**，列表标题 24px，次要信息 12px
  - 两端**都用 24px 正文**的好处：同一套气泡九宫格素材直接通用，只是拉伸宽度不同

### 13.4 地图场景尺寸（横竖都要成立）

办公区**不做成严格单屏**，而是**约 1.5 屏**（比一屏略大），相机跟随玩家：

- 横屏：横向看到更多工位
- 竖屏：纵向看到更多通道
- 场景设计时保证**关键路径在两种视野下都走得通**，指引线负责解决"看不见目标"的问题

### 13.5 素材的"两端通用"原则

| 素材 | 两端是否通用 | 说明 |
|---|---|---|
| 消息气泡九宫格 | ✅ 通用 | 只是拉伸宽度不同，**用同一套** |
| 头像框 / 贴纸 / 图标 | ✅ 通用 | |
| 地图瓦片 / 家具 / 角色 | ✅ 通用 | 横竖版同一套（不像场景整图需要两版） |
| 聊天三栏外壳 | ⚠️ **仅 PC** | 移动端不用三栏 |
| **移动端聊天顶栏**（返回 + 群名 + 更多） | ❌ **需新增** | |
| **移动端底部输入栏** | ❌ **需新增** | |
| **地图上的手机按钮**（带红点） | ❌ **需新增** | 移动端专用 |

> 好消息：**因为地图是瓦片拼的，不需要做横竖两版场景图**——
> 这一点比旧方案的"整张背景图"省一半素材（整图必须出横竖两张）。

### 13.6 验证方式

沿用我已经在用的双端自检：**同一份代码，两个视口各截一组图**，断言：

- 画布尺寸精确等于内部分辨率 × 整数倍
- HUD 与画布**重叠为 0**（PC）/ 覆盖率 < 5%（手机）
- 无横向溢出、无脚本错误

## 15. 静态样机（写码前的低成本验证）

### 为什么先做样机

**UI 美观度 80% 取决于素材，20% 取决于代码布局。**
所以现在最该验证的不是代码，是"素材拼起来到底好不好看"。

现在的问题很明确：**小游戏现有的 UI 是"网页仪表盘"风格**（深色卡片 + 圆角 + 系统字体），
和像素素材放在一起是两种语言。手机模式如果直接开写，会是最难看的组合：
**像素头像 + 平滑系统字体 + CSS 圆角气泡**。

### 样机要出 4 个视图（双端各 2 个）

1. **PC · 手机模式**：三栏布局 + 群聊刷屏 + 三选项
2. **PC · 地图模式**：办公区 + 主角 + 指引线 + 交互点
3. **手机 · 聊天模式**：全屏两级导航的聊天页
4. **手机 · 地图模式**：竖屏视野 + 手机按钮 + 指引线

用**事件一的真实对话**填内容（5 个人说话 + 时间戳 + 入群邀请卡 + 三选项）。

### 样机能看到什么

- 中文像素字体在 24px 下清不清晰、和像素框配不配
- 气泡九宫格拉伸后边角会不会变形
- 像素头像 + 像素气泡 + 像素字体的**三者气质是否统一**
- 竖屏视野下办公区够不够看

**好看 → 按 §16 的批次补素材，代码照样机写；不好看 → 改设计，只损失一两小时。**
